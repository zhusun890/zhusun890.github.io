近期，DeepSeek Harness 团队发布了《Super-agent 设计探索：迈向更自主的 Agent 系统》，并同步开源了原型仓库 dsh-superagent-prototype。本文将阐述笔者在读完文章和源码后的想法。

Super-agent

Super-agent 的核心是一个“Router + Worker”双层结构（代码里分别对应 orchestrator 和 worker，文档中也称作 main session 和 executor session）。

每个 Super-agent 部署都绑定单个 repository，维护一个 Router session 和多个 Worker session。系统会从多个渠道，例如 GitHub (PRs, issues, etc.)、飞书接收信息，并通知 Router 和 Worker。Router 在接收到来自 "threads" 的消息后 (例如 GitHub 上一个 issue 或一个 pr 就算一个 thread)，可以执行以下操作:

  • 接收任务。 Router 创建一个新的 “Ticket” 并自动为这个 Ticket 分配一个 Agent (worker session)。Ticket 会记录该任务的各种信息，例如标题、代号、以及不超过 30 词的备注消息，这些信息也会被发送给 worker，worker 也可以在工作过程中更新 ticket 状态。Ticket 创建完成后，为用户回复一句确认消息; 对于后续发生在这个 thread 上的新消息将直接被转发给 worker。
    (例如: 你开了一个 issue (并 @ 了 dsh)，这个 issue 最开始会被发给 router，然后如果 router选择接收任务，创建 ticket，接下来在这个 issue 里发的 comment 会被直接发给对应ticket 绑定的 worker session)

  • 分配任务到现有的 Ticket。 Router 可以将新的 thread 绑定给已有的 ticket, 并让 ticket 绑定的 worker session 工作

  • 停止任务。 被明确要求停下某个 ticket 时，Router 可以终止该 ticket。

  • 忽略。 什么都不做。

很明显这里 Router 完全不拆解任务，他们不理解任务，他们只是任务的搬运工。每个 worker 都会在自己的 git worktree 里工作，所以它们彼此看不到其他人 (或者 agent) 改了什么，在他们改的过程中其他 agent 的改动也不会影响他们，但合并的时候就难说了。

Pros

想象你写了一个小脚本，自动检测 GitHub 上特定仓库有没有新的 (符合条件的) PR 和 issues，为这些 PR 和 issue 启动独立的 Claude Code + worktree，并将对应 PR 和 issue 下方的新评论再直接转发给各自的 Claude Code 完成工作

这几乎就是 Super-agent 的最简工作方式，而它额外引入一个 Router 来在更复杂的信息环境下 (例如飞书群聊) 中提取消息，判断内容，并根据上下文选择 attach 到现有 ticket 还是创建新的 ticket。

那么它在理想情况下的好处也许就是并发较高且省心智，你以及其他的维护者，可以在多个地方随时随地要求你的 Agent 干活，可以想到什么说什么 (然而实际上并不太行, 见后文)，以往要这么做通常还需要手动维护多个 agent 窗口，针对每个窗口描述需求，并审查每个窗口的产出，通常是一大坨 diff 和一篇车轱辘话来回说的 Markdown 总结。

同时对于通过多条请求来下达的、完全可以并发的任务，它也会分成多个任务来并行执行，这样就更省时间 (也会更快地燃烧你的额度) 了。

Cons

然而笔者发现在 dsh-superagent-prototype 中默认要求 Router 只在请求明确指向已有 ticket 时才 attach，否则默认创建。

dispatch.md

Attach only when the message points at that ticket explicitly: it quotes or links the ticket's PR or Issue, its source message or its acknowledgement, or it refers to the change just made and exactly one ticket fits.
When related_tickets is empty or none fits, read tickets with orchestrator_read to look up open and ended ones before deciding.
A message on a similar subject is a new request: accept or ignore it, never attach it.
A duplicate ticket can be closed; a wrong attachment subscribes the ticket to the whole thread and stays.

笔者认为 Super-agent 在产出效果上的边际效应有限，更多像一个 scaffold 来让用户方便高效管理一个大项目中多个能够并行 build 的功能，当然 router 并不会为你判断任务是否可并行。

由于 workers 间 context 不共享，信息瓶颈还可能会让产出质量更糟: 比如说如果两个模型的任务实际上有某种 implicit dependency 关系，他们很可能只能在自己的 worktree 里改自己的东西，而完全不知道其他 agent 改了什么，并且这种 dependency 关系往往不仅限于代码任务里。

Router 可能面临一个先有鸡还是先有蛋的问题，如果你不去完成任务，你就很难穷尽两个任务之间的依赖关系。

令人忍俊不禁，除了第一个简单场景，在剩余 3 个场景中 Router 没有处理任何任务和 ticket 之间的依赖关系。这样的话我们大概率会收获一大堆存在冲突的 worktree，同时消耗了更多的 token，并且最后我们还是要解决冲突。

原文也基本没有就这类情况进行讨论，Section 7.1 (消融实验) 只测量了任务完成所消耗的时间 (以及 token usage)，实际任务则使用了耗时长的 mock tool 代替:

《Super-agent 设计探索：迈向更自主的 Agent 系统》7.1 章

7.1 消融实验

我们用群聊和 GitHub CI 消息流同时驱动四种端到端方案：单次实验包含约 300 条消息，其中约 20 条是工作请求，其余是闲聊、跟进、叫停和 CI 消息。编码工作用一个只消耗时间的工具代替，因此实验衡量的是系统的调度与协作能力，而非对单个任务的执行能力。每种方案重复运行 5 次。

笔者曾以为大伙 vibe coding 是为了产出，看来笔者过时了，大伙已经富裕到开 ultracode 类似物烧 token 玩而不在意产出质量的地步了。

哪怕我们不考虑简单的、只耗时的 mock tool 是否真的能够代表真实 coding task 中的 load 和耗时，笔者也认为这就像是在多线程环境里把 ConcurrentHashMap 换成不加锁的 HashMap 并删除 ConcurrentModificationException，然后宣布吞吐量大幅提升。虽然我们没检查效果，我们只是“衡量了系统的调度能力”，但你就说 clock time 是不是降低了吧！

Then

笔者认为，质量的瓶颈在于并行的 workers 在任务过程中的通信手段。

例如，Router 模型 (orchestrator, coordinator, leader, whatever you call it) 依然可以从 ReAct 中取得某种启发: 成为响应式的调度器，而不是 "one time forward pass" 的路由器

但是这需要 router 是一个足够强的模型，能“隐式维护”某种 dependency hierarchy graph，至少理解每个模型在做什么，因为 worker 自己不知道其他 workers 在干什么，也不知道自己的改动会不会破坏其他 worker 的依赖，因此也不会报告这些给 router。

最合适的协作方式可能会在 agentic RL 的 sandbox 中涌现，如果用类似设计的 harness 训练模型，模型确实就有可能（只是有可能）会学会预判依赖关系并报告。并且对于这样一个全新且 model 并不熟悉的架构，社区的 harness 设计需要和训练联动，否则只靠 zero shot 或 system 里的几个例子，模型可能根本就不理解怎么在这个庞大的 agent network 里行动和协作，指望模型在数百 K 上下文中对那几个可怜的例子保持强大的 ICL 能力，笔者觉得非常困难

(当然这属于另一个问题，也就是为 subagents (或者没有 leader agent 的 agent network) 寻找一个有效的通信协作机制并推广，目前仍然在探索当中)
